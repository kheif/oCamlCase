Reading Compiler Errors

The OCaml compiler is the best teacher you have. Its error messages follow a small number of patterns; once you can read them, most "mystery" errors become one-line fixes.

The anatomy of a type error

Almost every type error has the same shape: a location, the type the expression has, and the type the context expected.

terminal 
let x = 1 + 2.5;;

Error: This expression has type float but an expression was expected of type int

Read it backwards: the context (+, integer addition) expected an int; the highlighted expression (2.5) has type float. Two valid fixes, depending on intent: 1 + int_of_float 2.5 or 1.0 +. 2.5. OCaml never converts numbers silently, and + and +. are different operators.

Key habit

Do not ask "why is the compiler wrong". Ask "which of the two types in this message is the one I actually meant". The error names both sides of the disagreement; you only have to pick the side that matches your intent and change the other.

The five errors you will meet first

1. Arithmetic operators

This expression has type float but an expression was expected of type int: you mixed + with floats or +. with ints. Integer math uses + - * /, float math uses +. -. *. /..

2. Too few arguments, no error at all

terminal 
let add x y = x + y
let r = add 3;;

val r : int -> int = <fun>

Because of currying, forgetting an argument is not an error: you get a function back. The error appears later, when you try to use r as an int: This expression has type int -> int but an expression was expected of type int. Whenever you see a function type where you expected a value, look for a missing argument upstream.

3. Branches that disagree

terminal 
let f b = if b then 1 else "one";;

Error: This expression has type string but an expression was expected of type int

Both arms of an if, and all branches of a match, must have the same type. The compiler types the first branch, then holds every later branch to it. The location always points at the later branch, but the bug may be in the first one.

4. Non-exhaustive match

terminal 
let head = function x :: _ -> x;;

Warning 8: this pattern-matching is not exhaustive.
Here is an example of a case that is not matched: []

This is a warning, not an error, and it is a gift: the compiler constructs a concrete value your code will crash on. Treat warning 8 as an error; either handle the case or make the failure explicit with an option (see Options and Result).

5. The mysterious 'a in a reported type

When a message mentions 'a list or 'a -> 'b, the compiler has not yet learned the concrete type; it is telling you the expression is polymorphic (see Polymorphism). The mismatch is usually between a generic function and a concrete use site.

When the error location looks wrong

Type inference flows through your whole program, so a mistake in one place can surface as an error somewhere else, often later in the file. Two tools for pinning it down:

Add annotations. Writing the type you believe a binding has turns a far-away error into a local one. The annotation acts as a checkpoint: inference cannot drift past it.

Once the code compiles, you can delete the annotations again, or keep the ones that read as documentation.

annotate.ml 
(* the error now appears HERE, not 30 lines later *)
let parse_age (s : string) : int =
  int_of_string s

Shrink the expression. Paste the failing expression alone into the Playground and rebuild it piece by piece, checking the inferred type of each piece. The piece whose type surprises you is the bug.

Reading val lines as a habit

The toplevel prints the inferred type of every binding. Before moving on, check that each val line matches what you intended. A function that compiles with the type 'a -> 'b -> 'a when you meant int -> int -> int compiles all the same; the type is the earliest place a logic error becomes visible.
