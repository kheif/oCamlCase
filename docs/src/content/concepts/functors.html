Functors

A functor is a module that takes another module as an argument. Where ordinary polymorphism abstracts over a type, a functor abstracts over a type plus the operations that come with it.

The problem functors solve

Suppose you build a set data structure. To keep elements sorted you need a comparison. For int sets you want integer comparison; for case-insensitive string sets you want a different one. Passing the comparison to every call invites inconsistency: two calls with different comparisons would silently corrupt one set.

The set implementation really depends on a package: a type t together with a compare for that type. Modules are exactly such packages, so the set should be parameterized by a module.

Defining and applying a functor

A functor is written like a function whose parameter is a module constrained by a signature.

Applying it with MySet (IntOrd) produces a brand-new module. Each application is a separate module with its own abstract types, so a set of ints and a set of strings can never be mixed up.

my_set.ml 
module type ORDERED = sig
  type t
  val compare : t -> t -> int
end

module MySet (Ord : ORDERED) = struct
  type elt = Ord.t
  type t = elt list          (* sorted, no dups *)

  let empty : t = []

  let rec add x = function
    | [] -> [x]
    | y :: ys as s ->
        match Ord.compare x y with
        | 0 -> s
        | n when n < 0 -> x :: s
        | _ -> y :: add x ys

  let mem x s = List.exists (fun y -> Ord.compare x y = 0) s
end
use_set.ml 
module IntOrd = struct
  type t = int
  let compare = Int.compare
end

module CiStr = struct
  type t = string
  let compare a b =
    String.compare (String.lowercase_ascii a) (String.lowercase_ascii b)
end

module IntSet = MySet (IntOrd)
module NameSet = MySet (CiStr)

let s = IntSet.add 3 (IntSet.add 1 IntSet.empty)
let has = NameSet.mem "Ada" (NameSet.add "ada" NameSet.empty)
(* has = true: comparison is case-insensitive *)
Key insight

The comparison is fixed once, at the moment the module is created, instead of being re-supplied at every call. The functor turns "a set library that hopes everyone passes the same compare" into "a set type that physically cannot be used with two different compares".

The standard library does exactly this

This is not a toy pattern: the real Set and Map in the standard library are functors with the same shape.

stdlib_set.ml 
module IntSet = Set.Make (Int)
module StrMap = Map.Make (String)

let squares =
  StrMap.(empty |> add "two" 4 |> add "three" 9)

Set.Make works on any module providing type t and val compare : t -> t -> int; Int and String happen to provide exactly that.

When to reach for a functor

  • A data structure or algorithm needs operations on its element type, not just the type (compare, hash, equality, printing).
  • You want two instantiations to be distinct types so they cannot be confused.
  • You want to swap an implementation (a real clock vs a fake clock in tests) without touching the code that uses it.

For abstracting over a single value or function, an ordinary higher-order function is simpler; reach for functors when a whole interface travels together. Functors shine in code organized as in Projects with dune and opam, where module boundaries are already doing work.
