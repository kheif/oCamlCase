Options and Result

Options and results make failure visible in the type. Instead of raising an exception, a function returns None or Error, and the caller is forced by the type checker to handle both outcomes.

The option type

The built in option type is a parameterized type with exactly two constructors.

Options are an alternative to exceptions for handling partial functions. Instead of raising an error, you return None for failure and Some value for success.

options.ml 
(* type 'a option = None | Some of 'a *)

let rec nth_opt xs n =
  if n < 0 || xs = [] then None
  else if n = 0 then Some (List.hd xs)
  else nth_opt (List.tl xs) (n - 1)

nth_opt [3; 4; 5] 3
(* Returns None instead of crashing *)

Pattern matching on options

An option is just a variant, so the natural way to consume one is a match with two branches. The exhaustiveness checker guarantees you never forget the failure case.

Compare this to a language where the failure case is a null you can silently dereference. Here, the only way to get at the x inside Some x is to go through a pattern that also names what happens for None.

Key point

The payload of Some has a different type than the option itself. int option is not int: the type system stops you from using a maybe-missing value as if it were definitely there.

safe_div.ml 
let safe_div a b =
  if b = 0 then None else Some (a / b)

let describe r =
  match r with
  | None -> "undefined"
  | Some q -> string_of_int q

describe (safe_div 10 2)  (* "5" *)
describe (safe_div 10 0)  (* "undefined" *)

The Option module

Matching every option by hand gets verbose when a computation has several maybe-failing steps. The standard library's Option module provides combinators that thread the None case for you.

  • Option.value o ~default unwraps with a fallback.
  • Option.map f o applies f inside the Some, leaving None untouched.
  • Option.bind o f chains a function that itself returns an option, flattening the result.
Pattern

A chain of Option.bind calls reads as a pipeline where any failing step short-circuits the rest, the same control flow exceptions give you, but visible in the types.

option_chain.ml 
(* Look up a user's age, double it, fall back to 0 *)
let age_of name =
  match name with
  | "alice" -> Some 30
  | _ -> None

let doubled_age name =
  age_of name
  |> Option.map (fun a -> a * 2)
  |> Option.value ~default:0

doubled_age "alice"  (* 60 *)
doubled_age "bob"    (* 0 *)

The result type

An option tells you that something failed, but not why. The built in result type carries a payload in both the success and the failure case.

Use result when the caller needs to distinguish failure modes or report a message. Ok wraps the success value; Error wraps a description of what went wrong, often a string or a custom variant.

Like options, results are ordinary variants: you consume them with pattern matching, and the exhaustiveness checker keeps both arms honest.

result.ml 
(* type ('a, 'e) result = Ok of 'a | Error of 'e *)

let validate_age n =
  if n < 0 then Error "age cannot be negative"
  else if n > 150 then Error "age is implausible"
  else Ok n

match validate_age (-3) with
| Ok n -> Printf.printf "age: %d\n" n
| Error msg -> Printf.printf "invalid: %s\n" msg

Exception, option, or result?

All three express "this computation can fail". They differ in who is forced to deal with the failure, and what information travels with it.

  • Exception: failure is invisible in the type. Good for truly exceptional situations and deep early exits (see Exceptions), but the compiler will not remind callers to handle it.
  • Option: failure is in the type, with no explanation attached. Good for lookups and partial functions where "not found" is self-explanatory.
  • Result: failure is in the type, with a payload explaining it. Good for validation and parsing, where the caller needs to know what went wrong.
Rule of thumb

Reach for option first. Upgrade to result when the caller needs a reason. Reserve exceptions for invariant violations and non-local exits where threading a value through every return type would obscure the code.
