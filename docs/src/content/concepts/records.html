Records

A record bundles named fields into a single value. Where tuples identify components by position, records identify them by name, which makes larger data shapes self-documenting.

Defining a record

A record type lists its fields and their types between braces. Building a value uses the same brace syntax with = instead of :. Every field must be given; there are no optional or default fields.

Field names live in the type definition, so OCaml infers the record type from the field names you use. If two record types share a field name, the most recently defined one wins, which is why field names are usually kept distinct per module.

Key point

Records are immutable by default, just like bindings. "Changing" a field means building a new record, the original is untouched.

account.ml 
type account = {
  owner : string;
  balance : int;
  active : bool;
}

let acct = { owner = "alice"; balance = 100; active = true }
(* acct : account *)

Accessing fields

There are two ways to read a record: dot access for a single field, and pattern matching to destructure several at once. When the binding you want has the same name as the field, you can use punning and write the field name alone.

access.ml 
(* Dot access *)
acct.balance                  (* 100 *)

(* Pattern matching with explicit names *)
let describe { owner = o; balance = b; _ } =
  o ^ " has " ^ string_of_int b

(* Punning: field name doubles as the binding *)
let describe' { owner; balance; _ } =
  owner ^ " has " ^ string_of_int balance

The trailing _ in the pattern tells the compiler you are deliberately ignoring the remaining fields; without it, OCaml warns that the pattern does not mention active.

Functional update

The expression { r with field = v } builds a new record that copies every field of r except the ones you override. This is the record analogue of shadowing: nothing is mutated, you just construct the next state.

This pattern is the heart of state-as-values programming: a function takes the old record and returns a new one. The Bank Account exercise is built entirely on this shape: every deposit or withdrawal produces a fresh account.

Pattern

{ acct with balance = ... } reads as "an account like acct, except for its balance". Fields you do not name are copied unchanged.

update.ml 
let deposit amount acct =
  { acct with balance = acct.balance + amount }

let close acct =
  { acct with active = false }

let acct2 = deposit 50 acct
acct2.balance   (* 150 *)
acct.balance    (* still 100: the original is unchanged *)

Mutable fields

A field declared with the mutable keyword can be updated in place with <-. This is the record-level version of ref; in fact, 'a ref is defined in the standard library as a record with one mutable field.

mutable_field.ml 
type counter = { mutable count : int }

let c = { count = 0 }
c.count <- c.count + 1
c.count          (* 1: same record, contents changed *)

(* type 'a ref = { mutable contents : 'a } *)

Imperative features like this come with sharing and equality pitfalls. The Mutability page covers them in depth.

Records or tuples?

Rule of thumb

Tuples are fine for two or three components whose meaning is obvious from context, like the pair returned by List.split. The moment a reader could mix up the components, or you find yourself writing a comment to explain the positions, switch to a record and let the field names do the explaining.
