Testing and Code Quality

The type system catches a whole class of bugs, but not wrong logic. Tests cover the rest, ocamlformat ends style debates, and a few conventions keep a growing project readable.

What the types don't catch

let add x y = x - y has exactly the type you wanted and is still wrong. Types prove that pieces fit together; tests check that they do the right thing. In OCaml the two are complementary: because the compiler already rules out shape errors, your tests can focus purely on behavior.

Inline tests with ppx_expect

The lightest workflow is expect tests: a test prints something, and the expected output lives in the source next to it.

Run dune test. If output and expectation differ, dune shows a diff; dune promote updates the expectation when the new output is the correct one. This loop makes tests cheap to write and cheap to update.

lib/greet.ml 
let hello name = "Hello, " ^ name ^ "!"

let%expect_test "greeting" =
  print_string (hello "world");
  [%expect {| Hello, world! |}]
lib/dune 
(library
 (name greet)
 (inline_tests)
 (preprocess (pps ppx_expect)))

Test executables with alcotest

For a classic assertion-style suite in test/, alcotest is the common choice. Each test is just a function; the runner gives readable, colored output.

test/test_greet.ml 
let test_hello () =
  Alcotest.(check string) "greets by name"
    "Hello, world!" (Greet.hello "world")

let () =
  Alcotest.run "greet"
    [ ("hello", [ Alcotest.test_case "basic" `Quick test_hello ]) ]
What to test in OCaml

Spend tests where the types are weakest: boundary cases of your logic (empty list, zero, equal elements), properties that must hold for all inputs (sorting twice equals sorting once), and every function whose signature mentions option or result, because each None and Error branch is a documented failure path that deserves a test.

Formatting: ocamlformat

One dotfile ends all formatting discussion. Put a .ocamlformat file at the project root, then dune fmt rewrites every file canonically.

.ocamlformat 
version = 0.26.2
profile = default

Pinning the version matters: ocamlformat output changes between releases, and the pin keeps every contributor (and CI) byte-identical.

Conventions that scale

  • One concept per file. A file named invoice.ml that defines type t and functions over it reads naturally as Invoice.create, Invoice.total.
  • Write the .mli for any file with an invariant. Abstract types (see Modules and Signatures) make invariants unbreakable; tests then only need to cover the exported functions.
  • Make illegal states unrepresentable first, test second. A variant that cannot express the invalid case (see Variants and Constructors) is cheaper than any number of tests for it.
  • Keep dune test green and fast. A test suite that runs in seconds gets run; one that takes minutes gets skipped.
